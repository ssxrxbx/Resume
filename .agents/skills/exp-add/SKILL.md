# /exp-add — 경험 정리 (1단계)

포트폴리오의 진실 공급원에 경험을 **원자 단위(파일 1개 = 경험 1건)**로 추가한다.

## 경험 카테고리 (셋 중 하나로 분류)
```
portfolio/career/      car-*   경력 (인턴·연구실·군)
portfolio/activities/  act-*   대외활동 (동아리·서포터즈·연수·연합)
portfolio/projects/    prj-*   프로젝트 (구체 산출물)
```
- 활동 안에서 만든 산출물은 **프로젝트로 분리**하고 활동과 연결한다.
  (예: 동아리(act) ↔ 그 동아리에서 만든 서비스 2개(prj))

## 입력 형태 (셋 중 무엇이든)
1. 사용자가 자유롭게 풀어쓴 경험 설명
2. 기존 이력서/자소서/포트폴리오 파일 또는 텍스트 (임포트)
3. "정리할 게 있어" 만 말함 → **인터뷰 모드**로 질문하며 채움

## 절차
1. 경험을 career/activities/projects 중 하나로 분류. 해당 폴더에서 다음 번호 확인(가장 큰 prefix-NN + 1).
2. **경험 유형(`type`) 판정** — 아래 "유형 판정 규칙" 참고. 이게 스키마를 가른다.
3. 유형에 맞는 템플릿으로 `{prefix}-NN-{영문슬러그}.md` 생성 (episode = `career/activity/project.md`, container = `container.md`).
4. **episode면 STAR 4요소**를 채운다. **container면 개요·구성(하위 프로젝트)·전체 성과**를 채운다. 빈 요소·정량 누락이 있으면 사용자에게 되묻는다 (지어내지 않음).
   - R(결과)은 숫자·비율·규모·순위로. 정량값이 없으면 `quant: false` + "정량 보강 필요" 표시.

### 유형 판정 규칙 (episode vs container)
판정 기준은 하위 프로젝트 유무가 아니라 **"이 경험 자체를 하나의 STAR로 말할 수 있는가"**다.

| | episode | container |
|---|---|---|
| 정의 | 단일 사건·단일 서사 | 여러 산출물을 거느린 기간·소속 |
| 본문 | S / T / A / R | 개요 / 구성(하위 링크) / 전체 성과 |
| 예 | 프로젝트 1건, 단기 연수, 활동 자체가 하나의 스토리인 경우 | 다년 경력, 하위 프로젝트가 실질 산출물인 동아리 |
| STAR | 필수 | **없는 게 정상** (하위 프로젝트가 STAR를 담당) |

- **하위 프로젝트가 있어도** 활동 자체에 단일 서사가 있으면 episode다(하위는 링크만).
- **container에 STAR를 억지로 만들지 않는다.** 여러 사건을 한 STAR로 압축하면 전부 뭉개진다 — 그게 "정량 없는 두루뭉술한 경력 기술"의 원인이다.
- `material_ready`는 유형에 맞게 판정한다: episode = STAR+증거조각 / container = 개요+하위연결+증거조각. **container에 STAR가 없다는 이유로 `false`로 두지 않는다**(3단계가 "보강 필요"로 오판한다).
5. 역량 태그(`tags`)를 단다 — 이게 3단계 매칭의 핵심. **반드시 `portfolio/TAGS.md`의 표준 어휘에서만 고른다.**
   - 목록에 없는 새 태그가 꼭 필요하면, 먼저 `TAGS.md`에 추가·정의한 뒤 사용한다(동의어 분산 금지).
   - 의미가 겹치면 새로 만들지 말고 가장 가까운 표준 태그를 쓴다 (예: '업무효율화'는 `자동화`로).
6. **증거 조각(`## 증거 조각`) 작성** — 본문과 별개로, 그 경험에서 **답안에 그대로 꺼내 쓸 수 있는 원자 단위 사실**을 목록으로 뽑는다. 아래 "증거 조각 규칙" 참고. (3단계 `/answer`가 본문을 매번 재해석하는 대신 여기서 조각을 골라 조립한다)
7. **연결 설정**: 프로젝트면 `activity:`에 소속 활동 ID, 활동이면 `projects:[]`에 하위 프로젝트 ID.
   기타 관계는 양쪽 `related:[]`에 상호 기재. container면 하위 프로젝트를 `## 구성`에도 링크한다.
8. frontmatter의 `id`, `category`, `type`, `material_ready`, `quant`를 실제 상태에 맞게 설정.
9. **`portfolio/INDEX.md`를 frontmatter 기준으로 재생성** (⚠️ 아래 "INDEX 재생성 규칙" 참고 — 손으로 베끼지 말 것).
10. (Notion 미러가 설정돼 있으면) 해당 경험을 Notion에도 반영.

## 증거 조각 규칙 (`## 증거 조각`)
본문(episode의 STAR, container의 개요·성과)은 *서사*라 답안에 그대로 못 쓴다. 증거 조각은 그 서사에서 **꺼내 쓸 수 있는 사실만 원자 단위로 분해**한 목록이다. 답안 품질의 일관성이 여기서 나온다 — 같은 경험이 문항마다 다른 사실로 흔들리는 걸 막는다.

형식: `` - `[표준태그]` 검증된 사실 한 줄 (수치가 있으면 반드시 포함) ``

```markdown
## 증거 조각
> 답안 재조립용 원자 단위 사실. 태그는 TAGS.md 표준 어휘.

- `[분석]` 진입 시 API 12개가 동기 호출되는 구조를 지연 20초의 원인으로 규명
- `[커뮤니케이션]` 개발 측 기능 축소 요구를 "사용자에게 크리티컬한가" 기준으로 설득해 최종 스펙에 포함
- `[데이터]` 설문 32명·인터뷰 8건으로 초기 가설을 검증하고 방향을 수정
- `[실행력]` 2026.06 정식 출시
```

작성 규칙:
- **한 줄 = 한 사실.** 여러 사실을 접속사로 묶지 않는다(조립할 때 쪼갤 수 없어진다).
- **태그는 `TAGS.md` 표준 어휘에서만.** 한 조각에 태그 2개까지 허용(`[인프라][문제해결]`).
- **수치·고유명사는 조각에 그대로 넣는다.** 답안에서 정량이 누락되는 주원인이 "조각 단계에서 이미 뭉갠 것"이다.
- **검증된 사실만.** 해석·자평("~하는 역량을 길렀다")은 조각이 아니다. 조각은 *무엇을 했는가*이지 *무엇을 얻었는가*가 아니다.
- 개수는 경험 크기에 따라 **3~8개**. 너무 잘게 쪼개면 조립 비용만 커진다.
- 본문이 바뀌면 조각도 같이 갱신한다(조각은 본문의 파생물 — 본문에 없는 사실이 조각에 있으면 안 된다).
- **⭐ 조각 태그 ↔ frontmatter `tags` 정합 (필수)**: 조각에 단 태그가 frontmatter에 없으면 **그 역량으로 검색해도 이 경험이 안 걸린다**(조각은 근거를 갖고 있는데 색인에서 누락). 조각을 쓴 뒤 반드시 대조하고, 아래 기준으로 승격한다.
  - **승격**(frontmatter `tags`에 추가): 같은 태그가 **조각 2개 이상**에서 나오거나, **그 경험의 핵심 서사**에 해당할 때. (예: 그 경력을 대표하는 역량은 조각 1개여도 승격)
  - **조각에만 유지**: 조각 1개에서 부수적으로만 스치는 태그. 전부 올리면 태그 인플레이션으로 매칭 정밀도가 떨어진다.
  - 승격했으면 `INDEX.md` 태그별 인덱스도 재생성한다.

## ⚠️ INDEX 재생성 규칙 (drift 방지 — 가장 중요)
`portfolio/INDEX.md`는 **원본이 아니라 경험 파일 frontmatter의 파생물(derived view)**이다. 경험을 추가·수정·삭제하면, INDEX는 "기존 줄에 한 ID만 끼워넣기" 식으로 손보지 말고 **frontmatter를 단일 진실원(SSOT)으로 삼아 다시 만든다.**

재생성 절차:
1. `portfolio/` 전체 경험 파일의 frontmatter를 스캔해 `{id, category, type, title, period, tags, quant, material_ready, activity, projects, related}`를 모은다.
2. 이 데이터로 INDEX의 4개 섹션을 **전부 다시 산출**한다:
   - **카테고리별 표**(career/activities/projects): id·**유형(type)**·제목·기간·태그요약·정량·**재료(material_ready)**.
   - **연결 맵**: `activity`↔`projects`와 `related`에서 생성.
   - **태그별 인덱스**: 모든 파일의 `tags`를 뒤집어 `태그 → [ID...]` 역색인을 **처음부터 다시** 구성. (파일에 있는 모든 (태그, ID) 쌍이 빠짐없이 들어가야 함)
   - **보강 필요(TODO)**: `quant: false`거나 본문 "보강 필요"가 있는 항목.
3. **정합성 self-check (필수)** — 눈으로 훑지 말고 **검사 스크립트를 돌린다**:
   ```bash
   python3 portfolio/_check.py
   ```
   9개 항목(INDEX 행 수·태그 역색인 양방향·조각 태그 정합/승격 대상·연결 대칭·유형↔본문 구조·조각 보유·커버리지·재료 상태·계열 편중)을 한 번에 검사한다. **오류(❌)는 0이어야 하고**, 경고(⚠️)는 판단이 필요한 항목이니 하나씩 확인해 조치하거나 의도적 유지 사유를 남긴다. 어긋난 건 그 자리에서 고친다 — **INDEX가 파생물이므로 INDEX를 고친다(경험 파일을 INDEX에 맞추지 않는다).**
4. INDEX 상단 "최종 갱신" 줄에 날짜와 변경 요약을 남긴다.

> 원칙: 경험 파일(frontmatter)만 손으로 쓰고, INDEX는 거기서 **다시 뽑아낸다.** 이래야 색인 누락(매칭 누락)이 구조적으로 생기지 않는다.

> ⚠️ **애드혹 정정에도 동일 규칙 적용**: 신규 추가가 아니라 기존 파일의 **사실관계를 정정**할 때도 `tags`가 바뀌면 카테고리 표만 고치고 끝내지 말고 위 3번 self-check를 **태그별 인덱스 전체**에 다시 돌린다 — 카테고리 표만 고쳐 태그 인덱스에 유령 항목이 남는 게 반복되는 실수 패턴이다.

## 인터뷰 모드 가이드
한 번에 하나씩 묻는다: 상황 → 과제 → 내가 한 행동 → 결과(숫자) → 배운 점.
"그때 수치로 어느 정도였나요?" 처럼 정량화를 적극 유도한다.

> ⚠️ **강한 동사·외부검증형 성과는 한 번 더 확인**: "설계·구축·구현" 같은 강한 실행 동사나 "수상" 같은 외부 검증형 성과가 나오면 되묻는다 — "직접 만들어 돌려본 것인지 / 자료·논문 조사 수준이었는지", "정식 수상인지 / 발표 후 피드백인지". **과장은 이 두 유형에서 반복적으로 나오고, 1단계에서 안 걸러지면 3단계 답안 작성 중에야 발견된다.**

## 출력
- 생성/수정된 경험 파일 경로
- INDEX 갱신 요약
- 보강이 필요한 부분(정량 누락 등)을 명확히 알림
