# /company-analyze — 기업 분석 (2단계)

`companies/{회사명}/`에 `jd.md`·`context.md`·`fit-matrix.md`를 만든다. JD가 2개 이상이면 `jd-compare.md`도 만든다. **입력은 회사명 + 지원 직무 + JD(원문·URL)면 충분하다** — 회사 자료는 직접 찾는다.

## 0. 회사 리서치 (필수, 자료를 안 줘도 직접)
JD만 보면 직무 요건은 알아도 **회사가 어디로 가는지**를 모른다. 지원동기·기업핏은 후자에서 나온다.
- **먼저 모집 직무 전체 목록을 확보한다.** 사용자가 준 JD는 전체 선택지가 아니다. 공고문·JD북·채용 페이지에서 전체를 확보하고, 배제한 직무마다 근거를 1줄 남긴 뒤 좁힌다(순위가 뒤집힐 수 있다).
- WebSearch·WebFetch로 당해년도 우선 수집:

  | 찾을 것 | 쓰임 |
  |---|---|
  | 신년사·CEO 메시지 | 올해 방향·톤 → 지원동기 근거 |
  | 인재상·채용 페이지 문구 | 축② 인재상 |
  | 사업 구조·수익원·실적(IR·기사) | 축③ 내 직무가 닿는 수익·성장축 |
  | 최근 전략 이슈(전환·투자·신사업) | "회사를 이해하는 지원자" 차별화 |
  | 지원 부서·제품의 실체 | 그 조직이 실제로 하는 일 |

- **출처 링크를 항목마다** 단다. 원문이 막히면 다른 매체로 교차 확인하고 경위를 적는다. 추측을 회사 사실로 쓰지 않는다.
- **PDF·이미지 자료는 Read로 직접 보지 않는다.** `python3 portfolio/_extract.py <파일> {회사명}` → 목차 → `--find "직무 키워드"` → `--page N-M`으로 필요한 쪽만 읽는다. 도구 탐색을 하지 않는다(스크립트가 환경별 방식을 고르고, 「미추출」이면 하위 에이전트 지시문을 출력한다). 표가 깨진 쪽만 원본을 보고, **답안에 인용할 수치·필수 요건은 원본 쪽으로 확인한다**.
- 찾아도 자료가 없을 때만 context.md 폴백을 쓴다(리서치를 건너뛰지 않는다).
- JD가 여러 개면 jd.md를 JD별 섹션으로, fit-matrix도 JD별로 만든다.

## 1. jd.md
- JD 원문 보존, 필수/우대/핵심 키워드 분리, 직무가 원하는 사람상 한 줄.
- 필수역량이 스펙형("~경험 보유")인지 성향형("~을 즐기는 분")인지 표시한다 — `/answer`에서 증명 방식이 갈린다.
- **HR 관점 (포지션별, 냉정하게)** — 역량을 쪼개면 다 충족인데 사람 단위로 물음표가 남는 간극을 잡는다. 목적은 응원이 아니라 **떨어질 이유를 미리 찾는 것**이다. 단 사실이 아닌 약점은 만들지 않는다.

  **(a) 지원 유형** — 먼저 판정한다. 나머지가 전부 여기서 갈린다. 근거 한 줄을 남기고, 애매하면 리스크가 큰 쪽으로. **직전 지원의 유형·포지셔닝을 전제로 깔지 않는다.**

  | 유형 | 정의 | 전형적 강점 | 전형적 리스크 |
  |---|---|---|---|
  | 직무 정합 | 현재 직무 = 지원 직무 | 즉시 전력, 실무 깊이 | "같은 경력자 많은데 왜 이 사람, 왜 우리 회사?" |
  | 인접 이동 | 도메인 같고 역할 다름 | 도메인 이해, 협업 상대 관점 | "그 역할 실무는 안 해봤잖아" |
  | 전환 | 직무·도메인 모두 다름 | 다른 시각 | "왜 바꾸나", 적응·잔류 의문 |

  **(b) 탈락 사유 Top 3** — `profile.md`·`INDEX.md` 기준. 역량 공백뿐 아니라 경력의 결·연차·정합도 같은 사람 단위 리스크를 포함한다. 표: 순위 | 사유 | 성격(정합도/기술 공백/깊이/차별화) | 방어 가능성(서류/면접만/불가).

  **(c) 문항별 검증 의도** — 표: 문항 | 표면 질문 | 실제 판정. 문항 문구가 아니라 그 뒤의 진짜 질문이고, 유형에 따라 달라진다(예: 지원동기 — 정합이면 "왜 이 사람, 왜 우리 회사", 이동·전환이면 "왜 옮기고 해낼 수 있나"). **문항이 없는 전형**(서식 기입·과제형)이면 서식이 요구하는 축을 문항 자리에 넣는다 — 새로 만든 서식이면 그게 곧 이번 채용의 판정 기준이다. `/answer` 전략 카드의 HR 판정 질문이 여기서 나온다.

  **(d) 결정적 리스크 방어** — (b) 1순위를 무력화할 방향. 서류에서 막을 것 / 면접으로 넘길 것을 나눈다(서류에 긴 해명은 약점을 부각한다).

## 2. context.md (`/answer` 키워드 축②③에 대응, 축①은 jd.md)
- **[축②] 인재상·톤** — 올해 미는 방향·가치, 회사 톤(답안 문체 결정용).
- **[축③] 사업·수익 구조 (필수)** — 무엇으로 어떻게 돈을 버는지(핵심 사업·수익원·비중·성장축)와 **내 직무가 그 구조의 어디에 닿는지** 한 줄. 비면 답안이 "회사를 아는 지원자"로 차별화되지 못한다.
- 지원 조직·제품의 실체, 인용할 회사 키워드·문장. 항목마다 출처.
- **폴백** — 리서치해도 자료가 없으면 비우지 말고 모집요강·JD의 간접 신호(전형 방식, 정책 문구, 강조 표현, 우대 조건의 결)로 톤·방향을 채우고 상단에 `TODO: 자료 확보 시 보강`.

## 3. fit-matrix.md
- 먼저 `profile.md`(전공·어학·자격 같은 정형 요건)와 `skills.md`(툴·클라우드·언어별 숙련도와 근거 ID)를 대조한다. 태그로는 안 잡혀서, 빠뜨리면 이미 충족한 항목을 `⚠️ 확인 필요`로 잘못 남긴다.
- JD 역량을 `TAGS.md` 표준 태그로 환산해 INDEX와 매칭한다(TAGS.md 관계 규칙 활용: "기획" 요구 → 하위 태그도 후보).

  | 요구 역량/키워드 | 매칭 태그 | 매칭 경험 ID | 강도 (✅/△/✗/⚠️) | 메모/공백 |
  |---|---|---|---|---|

- 강점/공백을 분리해 요약하고, 공백엔 `/exp-add` 보강을 제안한다.
- **전부 ✅여도 "공백 없음"으로 끝내지 않는다.** 매칭표는 항목을 쪼갤수록 충족처럼 보이는 낙관 편향이 있어서, 요약에 지원 유형과 탈락 사유 Top 3를 다시 싣는다.

## 4. jd-compare.md (JD 2개 이상일 때만)
**적합도 %는 fit-matrix 강도에서만 파생한다**(임의 숫자 금지).
1. 요구역량을 필수/우대로 나눈다. 가중치 필수 2, 우대 1.
2. 점수: ✅ 1.0 / △ 0.5 / ✗ 0 / ⚠️ 확인 후 재점수(미확인이면 0.5 잠정 + 캐럿).
3. `적합도% = Σ(점수×가중치) / Σ(1.0×가중치) × 100`, 반올림.
4. % 옆에 근거 1줄(충족한 필수 / 빈 필수). 표: JD | % | 핵심 근거 | 결정적 공백.

- **수행업무 대응도(상/중/하) 열을 따로 둔다.** %는 요구역량만 계산해 JD 작성 스타일에 좌우된다(범용 소프트스킬만 쓴 JD는 점수가 뜬다). JD의 수행업무 불릿마다 경험 ID를 붙여 대응 없는 불릿 수를 센다. 두 축이 어긋나면 **수행업무 기준으로 실질 순위를 조정**하고 그 사실을 적는다.
- %는 방향성 추정치다. 우대 불릿이 2~3개뿐이거나 ⚠️가 많으면 정수 대신 **상/중/하 + 근거**로 쓴다. ⚠️가 순위를 흔들 수 있으면 결론에 명시한다.
- 결론: 최적 JD 1개와 이유 2~3줄. ±10%p 이내면 "우열보다 결이 다름". 순위형 지원서면 이게 1·2순위 근거다.

## 자가 평가 · 출력 · 세션 경계
- `/retro` 루브릭 B로 점검하고 개선점은 `IMPROVEMENTS.md`에 적는다.
- 출력: 생성 파일 경로 / 회사가 원하는 것·내 강점·공백 / 지원 유형 + 탈락 사유 Top 3 + 방어 방향(서류 vs 면접) / (JD 여러 개면) 순위표와 추천.
- 끝나면 `applications/{회사명}/session.md`를 템플릿으로 만들어 「지원 공통」(지원 직무·순위, 지원 유형, 알면 문항 상태표)과 분석 중 받은 이번 지원 전용 지시를 적는다. 그리고 "새 세션에서 `/answer {회사명} 이어서`로 시작하면 리서치 원문이 빠져 토큰이 줄어듭니다"를 한 줄로 제안한다.
